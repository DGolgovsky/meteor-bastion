# Meteor Bastion — контекст проекта для новой сессии

> Обновлено 2026-11-08. При старте новой сессии **обязательно заново получить HEAD ветки `master`**: сведения ниже — зафиксированный снимок, а не замена проверке текущего репозитория. После раунда 5 и внедрения плана по скриншотам сохранены новые проверки; конкретный SHA всегда получать из GitHub, а не из этого снимка.

## 1. Цель и границы

**Meteor Bastion** — мобильная вертикальная браузерная tower-defense / roguelite, ориентир по игровым референсам — **Galaxy Defense: Fortress TD**. Цель — максимально близкие к референсу ощущение боя, баланс, специализированные механики турелей, R&D-цепочки, HUD, экран прокачки и выбор этапов, но собственная реализация, собственная графика и названия проекта.

Пользователь просит не ограничиваться советами: **изучать актуальный код, исправлять ошибки, измерять баланс, менять механики, добавлять контент, прогонять тесты и пушить результат**. Ранее отдельно отмечал, что противники вообще не успевали доходить до базы; после изменений требуется проверять реальный **прорыв к базе**, а не только красивый DPS. Не ломать то, что уже исправлено, например Hive и Firewheel.

## 2. Репозиторий и технологии

- GitHub: https://github.com/DGolgovsky/meteor-bastion
- Рабочая ветка: **`master`** (в чате был подтверждён доступ к чтению и push; проверять заново при новом подключении).
- **HTML5 + CSS + обычный JavaScript, Canvas 2D.** Игровой релиз — **один автономный `index.html`**. Никаких npm, Vite, webpack, Phaser, компиляции TS, Unity/Godot/APK для этого проекта без отдельного решения пользователя.
- Код теперь **модульный**: `src/shell.html`, `src/js/*.js`, `src/order.txt`. Скрипт **`python3 build.py`** собирает одиночный `index.html`.
- Собранный `index.html` **не хранится в Git** (исключён через `.gitignore`). **Править только `src/`**, не пытаться исправлять отсутствующий `index.html` через GitHub.
- Запуск тестов: **`node tests/smoke.cjs`** (43 теста) и **`node tests/balance.cjs`** (12 × 2 seed-забега) — без npm; тесты собирают код из `src/` в памяти. GitHub Actions проверяет эти команды и сборку.
- `BALANCE.md` — текущие численные параметры, `README.md` — обзор. При противоречиях **источник истины — актуальные `src/js/00-config.js` и остальные исходники**, затем тесты, затем документация. Обновлять документы при изменениях.

**Порядок склейки из `src/order.txt`:** `00-config.js` → `01-state.js` → `02-units.js` → `04-waves.js` → `03-combat.js` → `05-update.js` → `06-render.js` → `07-ui.js` → `08-main.js`. **Не сортировать** модули по именам.

## 3. Текущая игра (проверять по HEAD)

- **12 этапов**: 1–3 по **20 волн**; 4–8 по **25 волн**; 9–12 по **30 волн**. Босс последней волны, следующий этап открывается за победу.
- **4 слота турелей** по очереди «край слева → край справа → центр слева → центр справа»; подвижный по горизонтали Guardian. Бой стартует с Guardian, башни выдаются карточками. Guardian стреляет из двух рук; недавние правки касались компактного тройного залпа.
- **11 турелей**: Sky Guard, Laser, Disruption Drone, Aeroblast, Thunderbolt, Beam, Firewheel Drone, Hive, Railgun, Tesla Coil, Gravity Vortex Gun. Есть **11 типов врагов**, сопротивления по типам урона, разделение големов, лечение соседей, скрывающиеся разведчики, ускоряющиеся штурмовики, чемпионы Elite.
- **Карты 1 из 3** за очки боя, R&D уровни до 45, **36 цепных карт T1/T2/T3** с требованиями R&D и предыдущей ступени, Combo, Super, отдельные улучшения юнитов.
- **Normal / Elite** имеют разные составы волн, чемпионов и множители. Награды/прохождения режимов отслеживаются отдельно.
- **Chips** покупаются за компоненты (урон, скорострельность, выживаемость базы). **Liveries** Classic/Arctic/Ember — косметика. Патруль, энергия, награды, главное меню и мобильный HUD присутствуют.
- **Локальное сохранение: `meteor-bastion-save-v1`, формат `v:1`**. Сохранять обратную совместимость с ранними сохранениями. **Никакой рекламы или механики удвоения за рекламу.**

## 4. Текущие боевые акценты и последние изменения

- **Не считать устаревшие описания источником текущей логики.** В проекте прикреплён старый файл «Meteor Bastion — текущие механики.md» по раннему `index.html` (тогда было 3 этапа, другие HP/скорости и одноразовые осы). Для новой работы он только **исторический снимок**.
- Последний проверенный HEAD `93911a7` (Round 4): **волны плотнее**; Guardian ослаблен до **12 DMG** и стреляет 4 раза/с, тройной залп плотнее; **Aeroblast — ближний дробовик из 5 дробинок**; **Hive**: осы живут ~8,5 с, эхоосы ~6,5 с, максимум 2 осы на цель; **Tesla**: последовательные рикошеты разряда с падающим уроном вместо одновременного удара по всем целям; дополнительные снаряды летят **параллельно**, а не веером; Laser не поворачивается вслед за целью во время импульса.
- **Hive — критический инвариант:** радиус действия улья ограничивает **только выпуск ос**. Вылетевшие осы перемещаются и ищут врагов **по всему полю**, даже вне дальности турели, с корректным перенацеливанием. Не возвращать логику одноразовых ос-камикадзе.
- **Laser:** ограниченный по времени импульс, **направление фиксируется в момент выстрела**; луч визуально доходит до края поля, но урон только на его линии; базовый CD сейчас **7,8 с** (проверять актуальный код).
- **Beam** отличается от Laser: последовательные сфокусированные тики по цели, с накоплением урона и улучшениями; **Sky Guard** — отдельные impact и explosion; **Firewheel** — долгоживущий отскакивающий диск, не обычный снаряд; **Gravity** — поле, притягивающее врагов и наносящее тиковый урон; **Disruption** — контроль/поля.
- **Текущие параметры в `src/js/00-config.js` при последней проверке:** `waveStart:5`, `waveGrowth:2.0`, `spawnBase:0.95`, `spawnReduction:0.008`, `waveHpGrowth:0.09`, `turretBasePower:1.6`, `MAX_ENEMIES:72`; поле `420×760`, нижняя линия базы `y=720`. Эти значения **наши**, не официальные параметры Galaxy Defense. Этапы усиливают HP/скорость; Elite сложнее Normal.
- В последнем `BALANCE.md` указано, что у базы **1000 HP, нет отдельного щита до Chips** — это изменилось по сравнению с ранними версиями. Актуальные значения всегда сверять с `newBattle()`.

## 5. Что найдено по оригиналу и как это использовать

Оригинальные игровые ориентиры, обсуждавшиеся в чате: Guardian подвижен; 4 слота заполняются в определённом порядке; турели имеют разные циклы огня и собственные T1/T2/T3 / Breakthrough / Combo цепочки; R&D ограничивает их появление; **Sky Guard: попадание + взрыв**, **Laser: луч, отражение, сканирование**, **Beam: сфокусированные тики (в гайдах ~145% ATK, 0,2 с, 20 тиков, базовый CD 10 с)**, **Hive: автономный рой**, **Firewheel: отскакивающий диск**, **Tesla: заряд, дуги, матрица**, **Gravity: стягивание противников**. Состав врагов, резисты и порядок карточек также значимы.

**Не выдавать числа Meteor Bastion за числа оригинала.** Универсальные «+8%/уровень», пороги драфтов, HP и интервалы волн, множители Elite и экономика — текущие игровые настройки и/или частично подтверждённые справочные сведения, не доказательство точного баланса Galaxy Defense. При проверке сторонних гайдов отличать версии игры и дату обновления. Визуальные референсы — 5 скриншотов, прикреплённых к исходному чату в проекте (мета-панель, Defeat, игровой процесс, три карты Level Up).

## 6. Состояние проверки и приоритеты на следующую сессию

- В `tests/smoke.cjs` после внедрения плана — **43 регрессионных теста**; **не утверждать, что все прошли**, пока не выполнен тестовый запуск на **новейшем** состоянии.
- Проверять **`python3 build.py`**, **`node tests/smoke.cjs`**, отсутствие JS-ошибок и работу на мобильном браузере. При недоступности runtime честно отделять синтаксические проверки, headless-симуляции и живое мобильное тестирование.
- Основные незавершённые направления: **массовые баланс-симуляции** по 12 этапам и Elite (включая несколько R&D-профилей), выяснение доли побед, числа прорывов, полученных карт, времени волн и DPS; **ручная визуальная проверка** на Android, интерфейса и FPS; дальнейшее сравнение с точной версией оригинала.
- Игрок должен **иногда получать урон базе уже в ранних волнах**, но не проигрывать заведомо до открытия защитных турелей. На высоких этапах важна реальная мета-прогрессия. Избегать обеих крайностей («все враги убиты у спавна» и «поражение на 2-й волне при любой сборке»).
- **Не терять принятые решения** из последующих пользовательских правок: геометрия и верхняя граница видимости, 120° дуга HP базы, компактный HUD, радиус Hive только на выпуск, фиксированный Laser, длинные осы/Firewheel, параллельные выстрелы.

## Результат плана по скриншотам, 2026-11-08

- Переработаны волны: `MAX_ENEMIES=110`, пачки/клин/россыпь, 11/36/64 врага на волнах 1/10/20 Stage 1 до этапной надбавки; снижение HP и скорости, движение с боковым дрейфом и паузами, исключён самопроизвольный полёт вверх. Прорывы базы измеряются в headless.
- Дальность Aeroblast 540 и адаптивная кучность из раунда 5 сохранены; Hive, Firewheel, Laser и формат сохранения `meteor-bastion-save-v1` — без регрессий.
- CI: [GitHub Actions](https://github.com/DGolgovsky/meteor-bastion/actions) запускает smoke 43, два набора по 12 headless и `build.py`. Наблюдение на 12 seed: первая победа разумного драфта 3-я, «первой картой» 4-я.
- **Открытая балансная проблема:** среднее видимое число врагов на волнах 1/10/20 ~4,3/9,2/11,6 (разумная стратегия) при целевых ≥8/≥28/≥40. Дальнейшую плотность настраивать вместе с DPS и выживаемостью, а не простым ускорением спавна. По телефону Pixel 10a ещё нужны проверка FPS и screenshot acceptance.
- Фазу 6 (краб, мины, скорость ×1.5, активные способности) не начинать без отдельного согласования.

## 7. Стандартный порядок работы агента

1. Прочитать **последний HEAD `master`**, последний коммит/diff, `README.md`, `BALANCE.md`, релевантные `src/js/*` и тесты.
2. Сопоставить запрос с действующей механикой **в коде** (а не с устаревшим резюме).
3. Исправить исходники `src/`; расширить регрессионные тесты и баланс-метрики, если меняется игровая логика.
4. Собрать `index.html` из модулей и выполнить доступные тесты/headless-прогоны. После правок убедиться, что `save v1` продолжает загружаться.
5. При наличии прав записи отправить результат в **`master`** (если пользователь не указал иное), проверить новый commit SHA.
6. В отчёте коротко привести **конкретные изменения, тесты/прогоны, commit SHA и известные ограничения**. Не сообщать об успешном push без подтверждённого коммита.
